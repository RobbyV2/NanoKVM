# USB passthrough

Exact runs `usb-proxy` against raw-gadget and needs the whole UDC. Hybrid projects the imported device through FunctionFS and keeps the HID functions.

Isochronous transfers are possible on this kernel and are refused by policy, not by hardware. In `raw_gadget.c` the only `usb_endpoint_xfer_isoc` test is inside the halt/wedge ioctl, which is correct per spec because an ISO endpoint has no halt condition; `raw_ioctl_ep_enable` and `raw_process_ep_io` do not test the transfer type at all. dwc2 sets `ep.caps.type_iso` on every non-ep0 endpoint and implements ISO throughout its gadget driver. Two limits bind instead: `raw_alloc_io_data` rejects an ioctl longer than `PAGE_SIZE`, and dwc2 rejects an ISO request longer than `mc * maxpacket`, so the real ceiling is one clamped packet per blocking ioctl. `--auto_remap_endpoints` already clears the high-bandwidth bits and clamps `wMaxPacketSize` to the UDC limit, which is what keeps the second limit satisfied. Nobody has measured throughput on hardware.

Both isochronous guards run before `SurrenderUDC` and stay on by default: a refusal before surrender costs nothing, a failure after it costs the keyboard and mouse until Stop. `AllowIsochronous` lifts them for one attempt. Recovery for that case rests on `Terminate` and on `raw_process_ep_io` waiting interruptibly, so SIGTERM breaks a blocked transfer out and the supervisor reclaims the UDC; the liveness watchdog does not cover it, because an interruptible wait reports `S` and not `D`.

The tier-2 VM cannot judge any of this. It never loads raw-gadget, and the `dummy_hcd.c` it builds from kernel.org v6.8 compiles zero isochronous endpoint capabilities — every ISO `EP_INFO` is commented out under "we don't provide isochronous endpoints since we don't support them". An ISO `USB_RAW_IOCTL_EP_ENABLE` there fails with `-EBUSY` and no gadget endpoints available, which is a fact about dummy_hcd and says nothing about dwc2. Treat a tier-2 isochronous result as a false negative.
